# LoℤqUL プロトコル仕様 (Draft 0.3)

LoℤqUL(ロジカル / `lozqul`)は、中央サーバーを持たない **P2P 分散型 SNS プロトコル**である。
本書は「基本的な SNS 機能」「ピアの発見」「データの肥大化防止」の 3 点を中心に定義し、
加えて **プロフィール画像・バナー画像(§4.5)** と、**CGI だけで動くシグナリング / blob 配信の HTTP ゲートウェイ(§11)** を詳細に定義する。

- 表記: ASCII 環境では `lozqul` と書く。URI スキームは `lozqul:`。
- キーワード MUST / SHOULD / MAY は RFC 2119 に従う。

---

## 1. 設計目標

1. **サーバーレス**: ユーザーのノードだけで動く。ブラウザ(WebRTC)のみでも参加できる。
2. **自己主権アイデンティティ**: アカウント = 公開鍵。メールや電話番号は不要。
3. **全データ署名付き**: 中継ノードを信用しなくても改ざん検知できる。
4. **有限ストレージ**: 全員が全データを持たない。各ノードは容量予算内で「自分に関係あるもの」だけを保持する。
5. **スパム耐性**: 発行コスト・レート制限・信頼グラフで緩和する。
6. **実装容易性**: JSON と Ed25519 / SHA-256 だけで実装できる。

### 非目標
- 全世界の全投稿の検索(検索は任意のインデクサノードに委ねる)
- 完全な匿名性(IP アドレス秘匿は Tor 等の下位層に任せる)

## 2. 用語

| 用語 | 意味 |
|---|---|
| ノード | LoℤqUL を話すプログラム1個 |
| ユーザー / 作者 | 鍵ペア1組。`pk` で識別 |
| イベント | 署名付きの1件のデータ(投稿・フォロー・リアクション等) |
| フィード | 1作者のイベント列 |
| ピア | 接続中の他ノード |
| ソーシャルピア | 自分がフォローしている作者(または、その作者を保持しているノード) |

| blob | hash(SHA-256 または Merkle ルート)で指すバイナリ。画像など(§7.4) |
| ゲートウェイ | HTTP(CGI 可)で、シグナリング・blob 配信・イベントの預かりを補助するサービス(§11) |

## 3. アイデンティティと鍵の形式

### 3.0 表記規約(全章共通)

| 対象 | 規約 |
|---|---|
| hex | 小文字、`0x` なし。公開鍵・イベント ID は 64 文字、署名は 128 文字 |
| base32 | RFC 4648 のアルファベット、**小文字、パディング `=` なし** |
| base64 | RFC 4648 §4 の標準アルファベット、`=` パディングあり |
| 整数 | 符号なし、0 〜 2^53−1 |
| 時刻 | UNIX 秒(UTC) |
| 文字列 | UTF-8。孤立サロゲートを含むものは不正 |
| 鍵・ID の**ワイヤ上の表現** | 常に hex(`pk`、タグ、フィルタ、`HELLO` など) |

> ワイヤ・タグ・フィルタに現れる公開鍵は **hex の `pk` のみ**。§3.2 の `uid` は、人間が入出力する場面(招待リンク、本文中のメンション、UI 表示)専用の表現である。

### 3.1 鍵

- 署名アルゴリズム: **Ed25519(RFC 8032)**。秘密鍵として保存・交換するのは **32 byte のシード**。公開鍵は 32 byte。
- 署名検証は **strict**: `S < L`、`A` と `R` が正準エンコード、`A` が小位数点でないことを検査する。
- 暗号化用 **X25519** 鍵は Ed25519 鍵から導出する(libsodium の `crypto_sign_ed25519_sk_to_curve25519` / `crypto_sign_ed25519_pk_to_curve25519` と同一)。
  - 秘密: `x_sk = clamp(SHA-512(seed)[0:32])`
  - 公開: Ed25519 公開点の y から `u = (1 + y) / (1 − y)`(Montgomery 形式)
- **ドメイン分離**: イベント署名は常に 32 byte の `id`(生バイト、hex 文字列ではない)に対して行う。イベント以外への署名は接頭辞 `"lozqul-<用途>-v1\0"` を付ける。
  - `HELLO`: `sig = Sign(sk, "lozqul-hello-v1\0" ‖ 相手の nonce)`
  - 鍵移行の所有証明: §3.5

### 3.2 ユーザー ID(`uid`)

```
payload = pk(32 byte) ‖ SHA-256("lozqul-uid-v1\0" ‖ pk)[0:2]     # 34 byte
uid     = "z1" + base32lower(payload)                             # 2 + 55 = 57 文字
```

- `z` は種別(ユーザー)、`1` は uid 形式の版。
- base32 の末尾の余りビットは 0 でなければならない(非正準な文字列は拒否)。
- 入力時の正規化: 前後の空白除去 → 小文字化 → チェックサム検証。**不一致は拒否**する(誤入力の検出)。
- 表示用の省略形は **先頭 8 文字 + `…` + 末尾 4 文字**(例: `z1aaaqea…xxxx`)。
- ダミー鍵(`pk = 00 01 02 … 1f`)の例:
  ```
  z1aaaqeayeaudaocajbifqydiob4ibceqtcqkrmfyydenbwha5dypygyy
  ```

### 3.3 秘密鍵のバックアップ形式

3 種類を定義する。いずれも元になるのは 32 byte の `seed`。

1. **秘密鍵文字列**
   ```
   "zsec1" + base32lower(seed(32) ‖ SHA-256("lozqul-seckey-v1\0" ‖ seed)[0:2])     # 5 + 55 = 60 文字
   ```
   画面に表示するときは必ず「共有・撮影・ログ出力しないこと」を警告する。
2. **ニーモニック(任意)**: BIP-39 英語単語リストの **24 語**。エントロピー 256 bit = `seed` そのもの(**PBKDF2 によるシード化はしない**)。チェックサムは BIP-39 の定義に従う。
3. **暗号化エクスポート**(拡張子 `.lozqulkey`、JSON):
   ```json
   {"v":1,"uid":"z1…","kdf":"scrypt","n":131072,"r":8,"p":1,"salt":"<base64 16byte>",
    "nonce":"<base64 24byte>","ct":"<base64>"}
   ```
   `key = scrypt(password, salt, N=n, r, p, dkLen=32)`、`ct = XChaCha20-Poly1305(key, nonce, seed, aad=uid)`。

### 3.4 ノード鍵とユーザー鍵

- `HELLO.pk` は **ノード鍵**。ユーザー鍵と同一でも別でもよい。
- 常時稼働の `relay` / `archive` ノードは **専用のノード鍵を使う**(SHOULD)。ユーザーの秘密鍵をサーバーに置かないため。
- ブラウザなどの **クライアント専用ノード**は、起動ごとの使い捨てノード鍵を使い、`caps` に `"client"` を入れる。DHT(§6.4)には参加せず、ピアレコード(kind 11)も発行しない。
- ゲートウェイ(§11)への認証にも、このノード鍵を使う。ブラウザは使い捨てのノード鍵で認証する。
- DHT のノード ID は `SHA-256(node pk)`。

### 3.5 鍵のローテーションと回復(kind 10)

```json
{"kind":10,"content":"{\"new\":\"<hex 新pk>\",\"reason\":\"rotate\"}","tags":[["newsig","<hex 128>"]]}
```

- **旧鍵**がイベントに署名し、`newsig` は **新鍵**による所有証明: `newsig = Sign(new_sk, "lozqul-migrate-v1\0" ‖ old_pk(32) ‖ new_pk(32))`。
- 受信側は両方の署名が有効なとき、移行宣言を保持する。旧鍵をフォローしているクライアントは「新アカウントに移行しますか?」と**確認を表示**する。自動フォローはしない。
- 旧鍵ごとに有効な kind 10 は **`seq` が最小のもの1件(先勝ち)**。
- **回復鍵(任意)**: プロフィール(§4.5)の `recovery` に別の公開鍵を登録しておくと、その鍵が署名した kind 10(`["old","<旧pk hex>"]` タグ付き、`newsig` は同様)が、旧鍵自身の宣言より**優先**される。旧鍵が漏洩した場合の乗っ取り対策。回復鍵はオフラインで保管することを推奨する。

## 4. データモデル

### 4.1 イベント

```json
{
  "v": 1,
  "id": "<hex sha256>",
  "pk": "<hex 32byte>",
  "seq": 128,
  "ts": 1764000000,
  "kind": 1,
  "tags": [["e","<event id>"],["p","<pk>"],["exp","1771776000"]],
  "content": "こんにちは、LoℤqUL!",
  "pow": 0,
  "sig": "<hex 64byte>"
}
```

| フィールド | 説明 |
|---|---|
| `v` | プロトコル版。現在 1 |
| `id` | 下記の正規化直列化の SHA-256(hex) |
| `pk` | 作者の公開鍵 |
| `seq` | 作者ごとの単調増加番号(0 始まり)。欠番検出と同期の効率化に使う |
| `ts` | UNIX 秒。±10 分を超えて未来のイベントは拒否 |
| `kind` | イベント種別(§4.2) |
| `tags` | `[名前, 値, ...]` の配列の配列 |
| `content` | UTF-8 文字列。kind により平文 or Base64 暗号文 |
| `pow` | 任意の nonce(§9.2) |
| `sig` | `id` に対する Ed25519 署名 |

### 4.2 正規化と ID

```
canonical = UTF-8( JSON( [ v, pk, seq, ts, kind, tags, content, pow ] ) )     # pk は hex 文字列
id        = SHA-256(canonical)                                                # 32 byte(wire では hex)
sig       = Ed25519.sign(sk, id)                                              # 生の 32 byte に署名
```

**直列化規則**(言語間で `id` を一致させるため厳密に定める)

1. 空白を一切入れない(`,` と `:` の前後も)。
2. 文字列のエスケープは次のものだけ。
   - `"` → `\"`、`\` → `\\`
   - U+0008 → `\b`、U+0009 → `\t`、U+000A → `\n`、U+000C → `\f`、U+000D → `\r`
   - 上記以外の U+0000〜U+001F → `\u00xx`(**hex は小文字**)
   - これら以外(`/`、U+007F、U+2028/2029、非 ASCII)は**エスケープせず UTF-8 のまま**。
3. 孤立サロゲートを含む文字列があるイベントは不正として破棄する。
4. 数値は 0 以上の整数のみ。小数点・指数・先頭ゼロ・`-0` は不可。
5. `tags` の内側の要素はすべて文字列。タグ名(先頭要素)は ASCII 英数字 1〜16 文字。

> JavaScript の `JSON.stringify`(孤立サロゲートを除く)と同じ結果になる。

- イベントの JSON 表現はワイヤ上で整形されていてもよい。受信側は parse した値を上記規則で**再直列化して `id` を検証**する。
- 仕様に無い追加フィールドは `id` に含まれないため無視し、転送時は取り除く。

**テストベクタ**(署名なし、`id` のみ)

```
pk      = 000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f
入力    = [1, pk, seq=0, ts=1764000000, kind=1, tags=[], content="こんにちは", pow=0]
canon   = [1,"000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f",0,1764000000,1,[],"こんにちは",0]
id      = 191028b2a139fec2b4ce3c07b6667c17af0103080bcd3cb8a1d6dfe9b68f78b7
```

### 4.3 サイズ制限
| 項目 | 上限 |
|---|---|
| イベント全体 | 8 KiB |
| `content`(kind 1, 2) | 4 KiB(約 1,300 文字の日本語) |
| `tags` 数 | 128(フォロー一覧 1 ページに `p` タグを約 100 個入れるため) |
| メディア本体 | イベントに含めない(§7.4 参照) |

### 4.4 kind 一覧

| kind | 名前 | 種別 | 既定 TTL | 説明 |
|---|---|---|---|---|
| 0 | profile | 置換型 | 無期限(最新のみ) | 名前・自己紹介・アイコン / バナー参照(§4.5) |
| 1 | post | 通常 | 365 日 | 本文投稿 |
| 2 | reply | 通常 | 365 日 | `e` タグで返信先を指定 |
| 3 | repost | 通常 | 90 日 | `e` タグで元投稿 ID、引用は content に |
| 4 | reaction | 短命 | 30 日 | content は `+` または絵文字。`e` で対象 |
| 5 | follow | 置換型 | 無期限(最新のみ) | フォロー一覧(`p` タグの列) |
| 6 | delete | 通常 | 365 日 | `e` タグの自作イベントの削除要求 |
| 7 | dm | 通常 | 180 日 | 暗号化メッセージ(§8) |
| 8 | mute | 置換型 | 無期限(最新のみ) | 自分用ミュート一覧(暗号化推奨) |
| 9 | checkpoint | 置換型 | 無期限(最新のみ) | 過去ログの要約署名(§7.5) |
| 10 | key-migrate | 通常 | 無期限 | 鍵移行宣言 |
| 11 | peer-record | 置換型 | 24 時間 | ピアの到達先(§6.3) |
| 12 | media-ref | 通常 | 投稿に従う | メディアのメタデータ(§7.4) |

- **置換型**: `(pk, kind, d)` ごとに `seq` が最大の 1 件だけが有効。`d` は `d` タグの値(無ければ空文字列)。古いものは破棄してよい。
- 既定 TTL は **`exp` タグが無い場合の推奨保持期間**。`exp` タグがあればそちらが優先(§7.1)。

### 4.5 プロフィール(kind 0)

#### 4.5.1 content のスキーマ

`content` は JSON オブジェクトを文字列化したもの。全体で 6 KiB 以下。**未知のフィールドは無視**し、再発行時に保持してもよい。

| フィールド | 型 | 必須 | 制約 |
|---|---|---|---|
| `v` | 整数 | MUST | `1` |
| `name` | 文字列 | MUST | 表示名。§4.5.2 |
| `about` | 文字列 | MAY | 512 byte 以内(UTF-8)のプレーンテキスト。改行は `\n` |
| `icon` | 画像オブジェクト | MAY | §4.5.3 |
| `banner` | 画像オブジェクト | MAY | §4.5.3 |
| `links` | `[{"label","url"}]` | MAY | 5 件まで。`label` 32 byte 以内、`url` は `https://` のみ・256 byte 以内 |
| `lang` | 文字列配列 | MAY | BCP 47、4 件まで |
| `dmrelay` | 文字列配列 | MAY | 3 件まで。ノードの hex `pk` または `wss://` アドレス(§8) |
| `home` | 文字列配列 | MAY | 3 件まで。ゲートウェイのベース URL(`https://` のみ・256 byte 以内、§11)。blob・イベントの取得先のヒント |
| `recovery` | 文字列 | MAY | 回復鍵の hex `pk`(§3.5) |
| `bot` | 真偽値 | MAY | 自動投稿アカウントなら `true` |
| `pinned` | 文字列 | MAY | 固定表示する自分の投稿の `id` |
| `verify` | 文字列 | MAY | `name@domain` 形式(§4.5.8) |

```json
{"v":1,"name":"あおい","about":"P2Pで遊んでいます",
 "icon":{"hash":"<hex>","mime":"image/webp","size":41230,"width":256,"height":256,
         "thumbhash":"<base64>","tiny":"<base64>"},
 "banner":{"hash":"<hex>","mime":"image/webp","size":180000,"width":1500,"height":500,
           "thumbhash":"<base64>"},
 "links":[{"label":"blog","url":"https://example.org/"}],
 "home":["https://example.org/cgi-bin/lozqul.cgi"],
 "lang":["ja"],"recovery":"<hex pk>"}
```

#### 4.5.2 表示名(`name`)

- 1〜32 書記素クラスタ、かつ 96 byte 以内。**NFC に正規化**する。
- 禁止する文字: 制御文字(U+0000〜U+001F、U+007F〜U+009F)、双方向制御(U+200E、U+200F、U+202A〜U+202E、U+2066〜U+2069)、U+200B、U+FEFF。U+200C / U+200D は文字・絵文字の結合に必要なので許可する。先頭・末尾の空白、連続する空白も不可。
- 違反しているとき、受信側はプロフィール全体を捨てず、**`name` を `uid` の省略形に置き換えて**表示する。
- **名前は一意ではない。** なりすまし対策として、クライアントは名前の隣に `uid` の短縮形を出すことを SHOULD とする(例: `あおい · z1aaaqea`)。未フォローの作者の `name` が、フォロー中の誰かと(NFKC + 大小無視で)同一のときは警告を出す。

#### 4.5.3 画像オブジェクト(`icon` / `banner`)

プロフィール画像(アイコン)とバナー画像は、kind 0 の `content` に**参照と最小限のプレビュー**だけを持たせ、本体は別の blob(§7.4)として配信する。

```json
{"hash":"<hex sha256>","mime":"image/webp","size":41230,"width":256,"height":256,
 "thumbhash":"<base64>","tiny":"<base64>","alt":"青い鳥のイラスト","color":"#3a6ea5"}
```

**フィールド**

| フィールド | 型 | icon | banner | 説明 |
|---|---|---|---|---|
| `hash` | hex 64 文字 | MUST | MUST | ファイル全体の SHA-256(小文字 hex) |
| `mime` | 文字列 | MUST | MUST | `image/webp` / `image/avif` / `image/png` / `image/jpeg` のいずれか |
| `size` | 整数 | MUST | MUST | ファイルのバイト数 |
| `width` / `height` | 整数 | MUST | MUST | ピクセル。ファイルのヘッダの値と一致すること |
| `thumbhash` | 文字列 | SHOULD | SHOULD | [ThumbHash](https://evanw.github.io/thumbhash/) の出力を base64(標準・パディングあり)にしたもの。デコード後 40 byte 以内 |
| `tiny` | 文字列 | MAY | 不可 | 64×64 の縮小版。`image/webp` を base64 にしたもの。4096 文字以内 |
| `alt` | 文字列 | MAY | MAY | 代替テキスト。140 byte 以内、改行不可、§4.5.2 の禁止文字は不可 |
| `color` | 文字列 | MAY | MAY | 代表色 `#rrggbb`(小文字)。読み込み前の背景色に使う |
| `focus` | `[整数, 整数]` | 不可 | MAY | 縦横比の違う枠に切り抜くとき残したい中心点 `[x, y]`。各 0〜1000(画像の左上が `[0,0]`、右下が `[1000,1000]`)。既定 `[500,500]` |

- **未知のフィールドは無視**する。
- 任意フィールドが不正なときは、そのフィールドだけを無視する。
- MUST のフィールドが欠けている・不正なときは、**その画像オブジェクト全体を無かったものとして扱い**(§4.5.6 の識別アイコンに戻す)、プロフィールの他の部分は捨てない。

**形状・寸法・サイズ**

| | `icon` | `banner` |
|---|---|---|
| 形状 | 正方形(`width == height`) | 縦横比 3:1(`2.85 ≤ width/height ≤ 3.15`) |
| 推奨寸法 | 256×256 | 1500×500 |
| 許容寸法 | 64×64 〜 256×256 | 600×200 〜 1500×530 |
| 最大ファイルサイズ | 64 KiB | 256 KiB |
| blob ID | ファイル全体の SHA-256 | ファイル全体の SHA-256 |

- どちらも 256 KiB 以下なので、blob ID は常に**ファイル全体の SHA-256**(Merkle ルートにはしない。§7.4)。
- 許容寸法の範囲外、または最大ファイルサイズ超過のオブジェクトは MUST のフィールドが不正なものとして扱う。

**共通ルール**

- `mime` は上記 4 種のみ。**SVG・GIF・HEIC・JPEG XL は不可**(スクリプト実行・巨大アニメ・デコーダの攻撃面を避けるため)。
- ファイルの先頭バイト(マジックナンバー)が `mime` と一致すること。

  | mime | 先頭バイト |
  |---|---|
  | `image/webp` | `52 49 46 46 ?? ?? ?? ?? 57 45 42 50`(`RIFF` + 4 byte + `WEBP`) |
  | `image/png` | `89 50 4E 47 0D 0A 1A 0A` |
  | `image/jpeg` | `FF D8 FF` |
  | `image/avif` | 先頭 4〜8 byte が `ftyp` ボックスで、メジャーブランドが `avif`(静止画のみ。`avis` は不可) |

- `hash` または `size` が取得した blob と一致しなければ破棄し、そのピアを減点する。
- **外部 URL による参照は禁止**。`url` 等のフィールドがあっても無視する(表示しただけで閲覧者の IP アドレスが漏れるため)。
- 公開側は **EXIF / XMP / ICC などのメタデータを除去する**(MUST。位置情報・撮影機材の漏洩防止)。受信側はメタデータを無視する(§4.5.5)。
- 受信側は `width × height > 4,000,000` の画像をデコードしない(圧縮爆弾対策)。
- **アニメーション**: 公開側は静止画を公開する(SHOULD)。受信側は先頭フレームだけをデコードし、残りのフレームは読まない(MUST)。
- **透過**: アイコンはアルファチャンネルを持ってよい。バナーは不透明にして公開する(SHOULD)。

#### 4.5.4 公開側の処理手順

画像を設定するクライアントは、次の順に処理する。

1. **デコード**: 入力ファイルをピクセル数の上限(4,000,000)付きでデコードする。超過・失敗は中止してユーザーに通知。
2. **向きの適用**: EXIF の Orientation をピクセルに反映する(以後 Orientation は使わない)。
3. **色空間**: sRGB に変換する(ICC プロファイルは埋め込まない)。
4. **切り抜き**: アイコンは正方形、バナーは 3:1 にする。ユーザーが範囲を選べる UI を提供する(SHOULD)。バナーは切り抜き後の中心点を `focus` に記録してよい。
5. **縮小**: 推奨寸法より大きければ Lanczos 等で縮小する(拡大はしない。許容寸法の下限に満たなければ拒否)。
6. **エンコード**: WebP を推奨する。品質は icon 80 / banner 75 から始め、最大ファイルサイズを超えたら 10 ずつ下げる(下限 40)。それでも超えるときは寸法を 90% に縮小して繰り返す。
7. **メタデータ除去の確認**: 出力ファイルを再解析し、次の表のチャンク等が**含まれていない**ことを確認する。

   | 形式 | 含めてはならないもの |
   |---|---|
   | WebP | `EXIF`、`XMP `、`ICCP` チャンク |
   | PNG | `eXIf`、`tEXt`、`zTXt`、`iTXt`、`iCCP`、`tIME`(許可: `IHDR` `PLTE` `tRNS` `IDAT` `IEND` `sRGB` `gAMA`) |
   | JPEG | APP1(Exif / XMP)、APP2(ICC)、APP13(Photoshop)、COM |
   | AVIF | `Exif` アイテム、XMP の `mime` アイテム、`colr` の `prof`(ICC)。色は `nclx` で表す |

8. **ハッシュ**: ファイル全体の SHA-256 を計算して `hash` と `size` を得る。
9. **プレビュー生成**: 画像を 100×100 以内に縮小して ThumbHash を作り `thumbhash` とする。アイコンは 64×64 の WebP(品質 70 目安、通常 1〜2 KiB)を作って `tiny` とする。任意で `color`(平均色)も付ける。
10. **kind 0 の署名**: 手順 8〜9 の結果を `icon` / `banner` に入れた新しい kind 0(`seq` を +1)を作って署名する。まだ発行(ネットワークへの送出)はしない。
11. **blob の保存と預かり**: ローカルの blob ストアに保存して **pin** する(§4.5.7)。`home` にゲートウェイがあれば、次の順に送る。
    1. kind 0 を `event.put`(§11.7)で預ける(ゲートウェイは参照先の確認に使う)。
    2. blob を `blob.put`(§11.6)で預ける。
12. **kind 0 の発行**: 手順 11 の**完了後**に、署名済みの kind 0 をネットワークへ発行する(購読者への `EVENT`、`INV`、§7.7)。**blob が取得できない状態で、参照だけを公開してはならない**(MUST)。`home` が無く作者ノードが blob を配信するときも、blob を pin してから発行する。

#### 4.5.5 受信側の検証

blob を取得したノード(クライアント)は、安価な検査から順に行う。1 つでも失敗したら破棄する。

1. **サイズ**: 受信中に `size` を 1 byte でも超えたら中断する。`size` が最大ファイルサイズを超える宣言は、そもそも取得しない。
2. **ハッシュ**: 全体の SHA-256 が `hash` と一致するか。不一致ならその**ピア(ゲートウェイ)を減点**する。
3. **マジックナンバー**: §4.5.3 の表と `mime` が一致するか。
4. **ヘッダ解析**: ファイルのヘッダから寸法を読み(全体デコードはしない)、`width` `height` と一致し、`width × height ≤ 4,000,000` か。形状・許容寸法の規則を満たすか。
5. **デコード**: 実装ごとの標準デコーダを使い、メモリ・時間の上限を付けて先頭フレームだけをデコードする。ブラウザでは `Blob` から `createImageBitmap` またはオブジェクト URL を使う。外部 URL を `<img src>` に直接渡さない。
6. **失敗時**: その `hash` を **24 時間の不良キャッシュ**に入れて再取得しない。表示は §4.5.6 の識別アイコンにする。デコードの失敗では、配信したピアを減点しない(作者側の不具合の可能性があるため)。

> `tiny` も同じ扱い: base64 を復号して 64×64 の WebP であること(マジックナンバー、ヘッダ寸法)を確認する。

#### 4.5.6 表示規則

**表示の優先順位**: キャッシュ済みのフル画像 → `tiny`(アイコンのみ)→ `thumbhash` のぼかし → `color` の単色 → 識別アイコン。

**アイコン**

- 丸・角丸などの形は**クライアントの自由**(画像自体は正方形)。
- 表示サイズが CSS 32px 以下のときは `tiny` を使い、それより大きいときだけフル画像を取得する。フル画像の取得は、そのアイコンが**画面に出たとき**に行う。
- 「画像を読み込まない」設定のとき(データ節約など)は、常に `tiny` または識別アイコンにする。

**バナー**

- 表示枠の縦横比は 3:1(デスクトップ)から 2:1(スマートフォン)まで変わりうる。枠に合わせて左右を切り抜き、`focus`(無ければ中心)を残す。
- 重要な要素は画像の**中央 2/3(幅の 66%)に収める**ことを、作者向けの UI で案内する。
- バナーは**プロフィール画面を開いたとき**に取得する(一覧表示では取得しない)。

**識別アイコン(identicon)**

画像が無い・不正・読み込み前のアイコンの代わりに表示する。`pk` から決定的に作り、**全クライアントで同じ見た目**にする(SHOULD)。

```
h    = SHA-256("lozqul-identicon-v1\0" ‖ pk(32 byte))
hue  = BE16(h[0:2]) mod 360
bits = BE16(h[2:4])                       # 下位 15 bit を使う
cell(r, c) = (bits >> (r*3 + c)) & 1      # r = 0..4(上から)、c = 0..2(左から)
もし 15 セルのうち 1 が 5 個以下なら、15 セルすべてを反転する。
列 3 = 列 1、列 4 = 列 0 として左右対称に 5×5 に展開する。
前景 = hsl(hue, 60%, 45%)、背景 = hsl(hue, 25%, 92%)
```

(テストベクタ: 付録 D.2)

**代替テキスト**: 画像に `alt` があれば `alt` 属性などで支援技術に渡す。無ければ「`name` のアイコン」のように補う。

#### 4.5.7 取得・保持・更新

**取得**

- **遅延取得**: 画面に表示する必要が出たときに取得する。
- **取得先の優先順位**: ① 手元のキャッシュ → ② 作者が `home` に書いたゲートウェイ(HTTP、§11.5)→ 接続中のピアのうち作者本人のノード → ③ DHT の保持者(§6.4)→ ④ `archive` ノード。メッセージは `WANT_BLOB`(§7.4)または HTTP の `blob`(§11.5)。
- 同じ `hash` の blob は 1 つだけ保存する(複数の作者が同じ画像を使っていても重複しない)。
- **再試行**: 取得に失敗したら、1 分 → 5 分 → 30 分 → 6 時間の順にバックオフする。4 回続けて失敗したら 24 時間は識別アイコンに固定する。

**保持**(§7.2 と連動)

| 距離 | アイコン | バナー |
|---|---|---|
| 自分 | フル画像を常に pin | フル画像を常に pin |
| d=1 | フル画像を保持(LRU の対象外) | LRU キャッシュ(§7.3。予算の 5% まで) |
| d=2 | `tiny` と `thumbhash` のみ(フル画像は保持しない) | `thumbhash` のみ |
| d=3 | 閲覧時のみ取得、24 時間の LRU | 同左 |

- `tiny` と `thumbhash` は kind 0 に含まれる。kind 0 は置換型で最新の 1 件しか残らないため、肥大化しない。
- アイコンの最大 64 KiB × フォロー数が予算に収まらないときは、§7.3 の手順で d=1 のアイコンを `tiny` に降格する。

**更新**

- 新しい kind 0 を発行すると旧 blob は参照されなくなり、受信側は **30 日後に GC** する。
- 受信側は `hash` が変わっていないとき、画像を再取得しない。
- 同一作者の kind 0 は **10 分に 1 件**まで受理する(超過分は破棄してよい)。
- 作者ノード(および `home` のゲートウェイ)は、現在の `icon` / `banner` を pin して配信を続ける。

#### 4.5.8 ドメイン検証(任意)

- `verify: "alice@example.org"` を宣言した場合、`https://example.org/.well-known/lozqul.json` の内容 `{"names":{"alice":"<hex pk>"}}` がそのプロフィールの `pk` と一致すれば検証済みとして表示してよい。
- 取得は**ユーザーがそのプロフィールを開いたときだけ**行う。バックグラウンドでの一括取得は禁止(IP アドレス漏洩・閲覧追跡の防止)。結果は 24 時間キャッシュする。
- 検証は表示上の付加機能であり、プロトコルの動作には影響しない。

### 4.6 kind ごとの content とタグの規則

| kind | `content` | 必須タグ | 任意タグ |
|---|---|---|---|
| 1 post | プレーンテキスト、1〜4096 byte | なし | `p`、`t`、`m`、`q`、`cw`、`exp`、`replaces` |
| 2 reply | 同上 | `e`(`root` マーカー) | `e`(`reply`)、`p`、`t`、`m`、`cw`、`exp` |
| 3 repost | 空文字列 | `e`(元投稿)、`p`(元作者) | `exp` |
| 4 reaction | `+` または絵文字 1 つ(1 書記素クラスタ、32 byte 以内) | `e`、`p` | `exp`(30 日以内を推奨) |
| 5 follow | 空文字列 | `d`、`p` を 0〜100 個 | `exp` なし |
| 6 delete | 理由(140 byte 以内、空でも可) | `e` を 1〜32 個 | なし |
| 8 mute | 暗号化した JSON(§8) | `d` | なし |

タグの書式

| タグ | 書式 | 備考 |
|---|---|---|
| `p` | `["p", "<hex pk>", "<petname>"?]` | `petname` は follow のときのみ、32 byte 以内 |
| `e` | `["e", "<hex id>", "<marker>"?]` | `marker` は `root` / `reply`。親が root のときは `root` だけでよい |
| `t` | `["t", "<tag>"]` | NFKC・小文字、`#` と空白を含まない、1〜64 byte、1 イベントに 8 個まで |
| `m` | `["m", "<sha256>", "<mime>", "<size>", "<thumbhash>"?]` | §7.4。4 個まで |
| `q` | `["q", "<hex id>"]` | 引用投稿(kind 1) |
| `cw` | `["cw", "<理由>"]` | 閲覧注意。理由は 64 byte 以内 |
| `d` | `["d", "<文字列>"]` | 置換型の識別子。64 byte 以内 |
| `exp` | `["exp", "<UNIX 秒>"]` | §7.1 |
| `replaces` | `["replaces", "<hex id>"]` | 編集(§7.8)。自分のイベントのみ |

**本文**

- プレーンテキストとして扱う。**HTML は解釈しない。** Markdown 等の装飾は任意のクライアント拡張。
- **メンション**: 本文に `@` + `uid`(57 文字)を書き、同じ `pk` の `p` タグを付ける。表示時は、`p` タグと一致した `@uid` だけを `name` に置き換える。メンションの `p` タグは 16 個まで。
- URL は `http://` / `https://` のみリンク化する。リンク先の自動プレビュー取得は行わない(IP アドレス漏洩防止)。

**フォロー一覧(kind 5)のページ分割**

- 1 イベント(8 KiB)に入る `p` タグは約 100 個なので、**`d` タグでページ分割**する(`["d","0"]`、`["d","1"]`、…)。
- 1 ページあたり `p` タグは最大 100 個、ページ数は最大 64(合計 6,400 人)。フォロー一覧は全ページの和集合。
- 各ページは置換型(`(pk, 5, d)` ごとに最新が有効)。ページを減らしたときは、不要になったページを空のフォローリストで上書きする。

## 5. トランスポートとワイヤプロトコル

### 5.1 トランスポート
| 環境 | トランスポート |
|---|---|
| ブラウザ | WebRTC DataChannel(シグナリングは §6.5) |
| ネイティブ | WebSocket / TCP+TLS(Noise XX も可) |
| 補助(共有サーバー等) | HTTPS(ゲートウェイ。§11) |

- 接続確立後、全メッセージは **JSON 配列 1 つ = 1 フレーム**(DataChannel / WebSocket のテキストフレーム)。
- 1 フレーム上限は 64 KiB。

### 5.2 ハンドシェイク
接続直後に双方が `HELLO` を送る。

```json
["HELLO", {"v":1,"pk":"<node/user pk>","caps":["relay","archive"],"ts":1764000000,"nonce":"<hex 16byte>","sig":"<hex>"}]
```
- `sig`: 相手が送った `nonce` に対する署名(接続先の鍵所有を確認)。
- `caps`: `relay`(他者のイベント中継可)、`archive`(長期保存を提供)、`index`(検索提供)、`stun`(シグナリング補助)。

### 5.3 メッセージ一覧

| メッセージ | 方向 | 内容 |
|---|---|---|
| `["HELLO", obj]` | 双方 | §5.2 |
| `["PING", n]` / `["PONG", n]` | 双方 | 生存確認(30 秒) |
| `["SUB", subId, filter...]` | → | 購読開始 |
| `["UNSUB", subId]` | → | 購読解除 |
| `["EVENT", subId or null, event]` | ← | イベント配送。`subId` が null なら拡散(gossip) |
| `["INV", [id, ...]]` | 双方 | 「このイベントを持っている」通知(gossip 用) |
| `["WANT", [id, ...]]` | 双方 | INV 等で知ったイベントの要求 |
| `["HEAD", pk, seq, id]` | 双方 | 作者フィードの先頭情報 |
| `["SYNC", syncId, pk, rangeData]` | 双方 | 集合差分同期(§7.6)。`rangeData` は negentropy v1 のメッセージ(hex) |
| `["PEERS", [peerRecord...]]` | 双方 | ピア交換(§6.2) |
| `["FIND", target]` / `["FOUND", target, [peerRecord...]]` | 双方 | DHT 探索(§6.4) |
| `["NOTICE", code, text]` | 双方 | エラー・警告 |
| `["BYE", reason]` | 双方 | 切断予告 |
| `["EOSE", subId]` | ← | 保存済みイベントの送信完了(§5.4) |
| `["SIGNAL", toPk, body]` | 双方 | WebRTC シグナリングの中継(§6.5) |
| `["WANT_BLOB", hash, firstIndex, count]` | → | blob のチャンクの要求(§7.4.2) |
| `["BLOB", hash, index, totalSize, base64, proof]` | ← | blob のチャンク 1 個(§7.4.2) |
| `["NOBLOB", hash]` | ← | その blob は持っていない(§7.4.2) |

### 5.4 フィルタ

```json
{"authors":["<pk>"],"kinds":[1,2],"since":1763000000,"until":1764000000,"e":["<id>"],"p":["<pk>"],"seqFrom":100,"limit":200}
```
- 全項目 AND。配列内は OR。`limit` を超える場合は新しい順に返す。
- `SUB` の後、保存済みイベントを返し終わったら `["EOSE", subId]` を送り、以降はリアルタイム配送する。

### 5.5 `NOTICE` のコード

`["NOTICE", code, text]` の `code` は次のいずれか。`text` は人間向けの説明(UTF-8、256 byte 以内、任意)。未知の `code` は無視する。

| `code` | 意味 |
|---|---|
| `invalid` | フレーム・イベントの形式が不正 |
| `sig` | 署名が不正 |
| `id` | `id` が再計算の結果と一致しない |
| `too-large` | サイズが上限を超えている |
| `rate-limited` | レート制限(§9.1)に達した |
| `pow-required` | PoW が足りない(必要なビット数を `text` に書く) |
| `expired` | `exp` を過ぎている |
| `unsupported` | 未対応の `kind`・`v`・機能 |
| `not-found` | 要求した対象(`SIGNAL` の宛先など)が見つからない |
| `blocked` | 相手のポリシーにより拒否された |
| `shutdown` | ノードが停止する |

## 6. ピアの発見

目標: **誰か1人に繋がれば、そこからネットワークに自力で参加できる**こと。
複数の仕組みを重ねて、単一障害点を持たないようにする。

### 6.1 ブートストラップ(最初の1ピア)

優先順に試す。

1. **招待リンク / ID 交換**
   ```
   lozqul://<uid>?hint=wss://example.org/lozqul&hint=https://example.org/cgi-bin/lozqul.cgi&hint=rtc:<signal-offer>
   ```
   - `hint` は複数指定でき、値は URL エンコードする(上の例は読みやすさのためエンコードを省略している。完全な例は付録 A.3)。種類は **スキームで判別**する: `wss://` = ノードへの直接接続、`https://` = ゲートウェイ(§11)のベース URL、`rtc:` / `rtcz:` = 手動の SDP 交換(§6.5.4)。
   - 友人から受け取った `uid` と到達先ヒントで直接接続する。QR コード化可。
   - 初回起動では「自分の ID を相手に渡し、相手の招待リンクを貼る」という **ID 交換方式** で成立する。
2. **保存済みピア**: 前回接続したピア(`peers.json`)に再接続。
3. **公開シードノード**: クライアントに数個の既定 `wss://`(および `https://` のゲートウェイ、§11)を同梱。**シードは単なる中継/ピア紹介役**であり特権を持たない。コミュニティが追加・差し替えできる(`seeds.json`、署名付きリスト配布も可)。
4. **DNS シード(任意)**: `_lozqul._tcp.<domain>` の TXT / SRV レコード。
5. **ローカル発見(ネイティブのみ)**: mDNS `_lozqul._tcp.local`。

### 6.2 ピア交換(PEX)

- 接続後、双方が最大 **16 件**の `peerRecord` を `PEERS` で送る(直近に接続成功したものを優先)。
- 受信側は署名と `ts`(24 時間以内)を検証し、候補テーブルに追加する。
- 15 分ごとに、ランダムな 1 ピアから追加で PEX を要求してよい。

### 6.3 ピアレコード(kind 11)

```json
{"kind":11,"pk":"<node pk>","ts":1764000000,"tags":[["addr","wss://node.example/lozqul"],["addr","rtc"],["caps","relay,archive"]],"content":"","sig":"..."}
```
- 自分の到達先(`addr`)を **自分の鍵で署名**したもの。偽装・改ざんできない。
- `addr` の値は次のいずれか(複数可、先頭ほど優先)。

  | 値 | 意味 |
  |---|---|
  | `wss://host[:port]/path` | WebSocket で直接接続できる |
  | `https://host[:port]/path` | **ゲートウェイ**(§11)のメールボックス経由で WebRTC を張れる。相手はそのゲートウェイを待ち受けている |
  | `rtc` | 共通の `relay` ピアの `SIGNAL` 中継(§6.5.1)経由でのみ接続できる |

- `rtc` や `https://` だけのノード(ブラウザなど)は、ゲートウェイや中継ピアを介してのみ接続できる。
- TTL は 24 時間。置換型。

### 6.4 DHT による「作者 → 保持ノード」探索

フォロー対象の投稿を持つノードを探すための、Kademlia 風の軽量 DHT。

- **ノード ID** = `SHA-256(node pk)`。距離 = XOR。
- ルーティングテーブル: k=16 の k-bucket。
- `["FIND", target]`:
  - `target` が **ノード ID** → 近いノードの `peerRecord` を返す。
  - `target` が **`SHA-256("feed:" + author pk)`** → 「その作者のフィードを保持していると自己申告したノード」の `peerRecord` を返す。
- **保持者アナウンス**: ノードは、フォローしている作者それぞれのキー `SHA-256("feed:"+pk)` に最も近い 8 ノードへ、自分の `peerRecord` を 2 時間ごとに登録(STORE)する。登録は 6 時間で失効。
- 結果として「作者 A の投稿を取りたい」→ DHT で保持者を見つける → `SUB` する、という流れになる(作者本人がオフラインでもよい)。

### 6.5 ブラウザ向けシグナリング(WebRTC)

ブラウザは受け入れポートを持てないため、WebRTC の SDP を**別の経路**で交換する。経路は次の 3 種類で、上から順に試す。

| 順 | 経路 | 必要なもの |
|---|---|---|
| 1 | **接続中のピアによる中継**(`SIGNAL` メッセージ、§6.5.1) | 既に 1 本でも接続があり、相手と共通の `relay` ピアがいる |
| 2 | **HTTP ゲートウェイのメールボックス**(§11.4) | 相手の `addr` に `https://…`(ゲートウェイ)がある |
| 3 | **手動交換**(招待リンクの `rtc:` ヒント、§6.5.4) | 人手で offer / answer を渡せる |

どの経路でも、運ぶ**本文(`body`)は同一**で、署名の規則も同じである。

#### 6.5.1 `SIGNAL` メッセージと本文

```json
["SIGNAL", "<toPk hex>", {"type":"offer","sid":"<hex 16文字>","from":"<hex pk>","ts":1764000000,
                          "sdp":"v=0\r\n…","sig":"<hex 128>"}]
```

| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| `type` | 文字列 | MUST | `offer` / `answer` / `ice` / `bye` |
| `sid` | hex 16 文字 | MUST | セッション ID(8 byte の乱数)。1 回の接続試行で offer・answer・ice・bye が共有する |
| `from` | hex 64 文字 | MUST | 送信者のノード `pk` |
| `ts` | 整数 | offer / answer は MUST | UNIX 秒。±300 秒を超えてずれた offer / answer は拒否 |
| `sdp` | 文字列 | offer / answer は MUST | SDP 全体。8 KiB 以内 |
| `sig` | hex 128 文字 | offer / answer は MUST、`ice` / `bye` は不要 | §6.5.2 |
| `cands` | 文字列配列 | `ice` のとき MUST | ICE candidate 行(`candidate:…`)。16 個以内、各 256 byte 以内 |
| `end` | 真偽値 | MAY | `ice` で、これ以上 candidate が無いとき `true` |

- 1 メッセージの `body` は **8 KiB 以内**(UTF-8 の JSON として)。
- **推奨は non-trickle**: ICE の収集が完了するまで(最大 3 秒)待ってから、candidate を含んだ完全な `sdp` を 1 通の offer / answer として送る。`ice` はこれで間に合わなかったときの補助。
- `from` は送信者の `HELLO` の `pk` と同じ**ノード鍵**でなければならない(§3.4)。

#### 6.5.2 署名と検証

```
sig = Ed25519.sign(node_sk,
        "lozqul-signal-v1\0" ‖ from(32) ‖ to(32)
        ‖ UTF-8(sid) ‖ 0x00 ‖ UTF-8(type) ‖ 0x00 ‖ UTF-8(ts を 10 進で) ‖ 0x00
        ‖ SHA-256(UTF-8(sdp)))                      # from, to は生バイト
```

- offer を受け取ったノードは、**answer を作る前に** `sig` を検証する(MUST)。失敗したら無視する(計算資源を使わせないため)。
- 経路上のノード(中継ピア・ゲートウェイ)は `sdp` を書き換えられない。書き換えると `sig` が合わなくなる。
- 署名の有無にかかわらず、最終的な相手の確認は接続後の `HELLO`(§5.2)で行う。`HELLO.pk` が `from` と違う接続は切断する(MUST)。
- `ice` と `bye` は署名しない。`from` は経路側で確認する(中継ピアは接続の `HELLO.pk`、ゲートウェイは認証トークンの `pk` と照合し、不一致なら拒否する)。
- `sid` の重複(同じ `from` から同じ `sid` の offer)は無視する。直近 10 分の `(from, sid)` を覚えておく。

#### 6.5.3 接続手順

```
A (ブラウザ)                経路                  B (ブラウザ)
  │ 1. offer を作成 ─────────────────────────────▶│
  │      (ICE 収集完了を最大 3 秒待つ)             │ 2. sig 検証
  │                                               │    answer を作成
  │◀───────────────────────────── 3. answer ─────│
  │ 4. sig 検証 → setRemoteDescription             │
  │═══════════ DTLS / SCTP DataChannel ═══════════│
  │◀──────────────── 5. HELLO(双方)────────────▶│
  │ 6. bye(任意)。以降、この経路は使わない         │
```

- **RTCPeerConnection の設定**: `iceServers` はゲートウェイの `ice`(§11.2)かユーザー設定の STUN。TURN は本仕様の対象外。
- **DataChannel**: `{label: "lozqul", negotiated: true, id: 0, ordered: true}`。両側が同じ設定で作るので `ondatachannel` を待たなくてよい。メッセージは**テキストフレーム**(§5.1)。
- **タイムアウト**: offer 送信から **30 秒**で DataChannel が開かなければ失敗とする。同じ相手には別の `sid` で最大 2 回まで再試行し、それでも駄目ならバックオフ(1 分 → 10 分 → 1 時間)する。
- **接続後**: 双方が `HELLO` を送り、ゲートウェイや中継ピアはそのセッションに関与しなくなる。

#### 6.5.4 中継ピアと手動交換

**中継ピアによる転送**

- `relay` ケイパビリティを持つピアは `["SIGNAL", toPk, body]` を受け取ったとき、`toPk` が**自分に直接接続中のピア**であればそのまま転送する。転送時に `["SIGNAL", toPk, body]` の形は変えない。直接接続中でなければ `["NOTICE","not-found","<toPk>"]` を返す(再転送はしない。**1 ホップのみ**)。
- 1 メッセージ 8 KiB 以内、**送信者ごとに毎分 20 回まで**(§9.1)。超過は `rate-limited`。
- 転送するかどうかは中継ピアの自由。転送しないときは `NOTICE` を返す。

**手動交換(`rtc:` ヒント)**

- 第三ピアもゲートウェイも無い最初の接続だけ、招待リンクの `hint=rtc:<データ>` を使う。`<データ>` は `body` の JSON(UTF-8)を base64url(パディングなし)にしたもの。圧縮する場合は `rtcz:` を前置し、deflate-raw で圧縮してから base64url にする。
- ID 交換方式(§6.1)では、A が offer を、B が answer を相手に(チャット・QR コード等で)渡す。

### 6.6 ピア選択ポリシー(接続スロット)

同時接続の既定は **24**(NAT 内ブラウザは 8〜12 でよい)。スロットを役割で分ける。

| スロット | 数 | 選び方 |
|---|---|---|
| ソーシャル | 8 | フォロー中の作者を持つピア。保持する作者が多い順 |
| DHT 近傍 | 6 | 自ノード ID に近い順(ルーティング維持) |
| ランダム | 6 | 候補テーブルからランダム(日食攻撃対策) |
| 長寿命 | 4 | 稼働時間・成功率が高いピア |

- **日食(Eclipse)攻撃対策**: 同一 /24 (IPv6 は /48) からは各スロット 1 本まで。ランダムスロットは 1 時間ごとに 1/3 を入れ替える。
- **スコアリング**: 有効イベント配送で加点、不正署名・スパム・不正フレームで減点。閾値以下は切断し 24 時間ブロック。

## 7. データの配信と肥大化防止

> **原則: 「全員が全部を持つ」を捨てる。**
> 各ノードは容量予算内で、**距離(ソーシャルグラフ上の近さ)と鮮度**に応じて保持する。
> 古いもの・遠いもの・短命なものから自然に消えるように設計する。

### 7.1 有効期限(`exp` タグ)

- イベントに `["exp","<UNIX秒>"]` を付けられる。
- `exp` 経過後、ノードは **そのイベントを保持も配信もしてはならない(MUST NOT 配信)**。削除は遅延してよい。
- `exp` を付けないイベントには kind ごとの既定 TTL(§4.4)を推奨保持期間として適用するが、**作者本人とそのアーカイブ提供ノードは超過保持してよい**。
- リアクション等の短命イベントは `exp` 付与を SHOULD とする。

### 7.2 距離による保持ポリシー

ソーシャル距離 `d`: 自分 = 0、自分のフォロー先 = 1、フォロー先のフォロー先 = 2、それ以外 = 3(未知)。

| d | 対象 | 保持するもの(既定) |
|---|---|---|
| 0 | 自分 | 自分の全イベント(無期限) |
| 1 | フォロー中 | 直近 **365 日** または 直近 **5,000 件** の多い方 |
| 2 | 2 ホップ | 直近 **14 日** または 直近 **200 件**。リアクションは保持しない |
| 3 | 未知 | **LRU キャッシュ**(自分のタイムライン・スレッド表示に出たもののみ。24 時間) |
| — | 自分宛返信・DM・メンション | d に関わらず 90 日保持 |
| — | プロフィール画像(icon / banner) | d≤1: icon はフル保持・banner は LRU / d=2: tiny のみ / d=3: 24 時間 LRU(§4.5.7) |

### 7.3 ストレージ予算とエビクション

- ノードは**容量予算** `B`(既定: ブラウザ 200 MiB、ネイティブ 2 GiB)を持つ。
- 使用量が `B` の 90% を超えたら、次の優先度の **低い方から**削除する。
  1. d=3 キャッシュ(古い順)
  2. 期限切れ(`exp` 超過)イベント
  3. リアクション(kind 4)・リポスト(kind 3)(d≥2)
  4. d=2 の古い投稿
  5. d=1 の 365 日超 or 5,000 件超の古い投稿
  6. メディアキャッシュ(§7.4。d≤1 のバナー画像を含む)
  7. d≤1 のアイコンのフル画像(`tiny` に降格する。自分のものは除く。§4.5.7)
- **削除してはならないもの**: 自分のイベント、自分のフォローリスト、自宛 DM、`pin` したもの。
- 削除しても**ヘッダのみ(`id`,`pk`,`seq`,`ts`)の「墓石(stub)」**を残してよい。同期時の再取得ループを防ぐため(最大 48 byte/件、30 日で消去)。

### 7.4 メディアの扱い(blob)

- **イベントに画像・動画を埋め込まない。** メディアは**コンテンツアドレス**(hash で指す)で別管理する。
- 参照は `media-ref`(kind 12)または投稿の `["m", "<sha256>", "<mime>", "<size>", "<thumbhash>"]` タグ。プロフィール画像・バナーは kind 0 の画像オブジェクト(§4.5.3)。
- サムネイル(≤ 2 KiB の ThumbHash / BlurHash 相当)だけをイベントに含めてよい。
- 本体は **作者ノード、`archive` ノード、および `home` のゲートウェイ(§11.5)**が提供する。
- 受信側は **閲覧時にオンデマンド取得** → LRU キャッシュ。事前複製しない。
- 上限: 画像 4 MiB、動画 32 MiB(既定。ネットワーク設定で変更可)。

#### 7.4.1 blob ID

| `size` | blob ID |
|---|---|
| 256 KiB(262,144 byte)**以下** | ファイル全体の SHA-256 |
| 256 KiB **超** | 16 KiB チャンクの **Merkle ルート** |

Merkle 木の定義:

- チャンク: 先頭から 16,384 byte ごとに分割する(最後のチャンクだけ短くてよい)。チャンク数 `n = ceil(size / 16384)`。
- 葉 = `SHA-256(0x00 ‖ チャンク)`。節 = `SHA-256(0x01 ‖ 左 ‖ 右)`。
- 各段で左から 2 つずつ組にし、**末尾に相手が無い奇数ノードは、そのまま上の段へ昇格**する(複製しない)。

**証明の検証**(チャンク番号 `i`、チャンク総数 `n`、証明 `proof[]`: 葉から根へ向かう兄弟ノードの列)

```
node = SHA-256(0x00 ‖ チャンク);  w = n;  k = 0
while w > 1:
    if i が奇数:           node = SHA-256(0x01 ‖ proof[k] ‖ node);  k += 1     # 右の子
    else if i + 1 < w:     node = SHA-256(0x01 ‖ node ‖ proof[k]);  k += 1     # 左の子(右の兄弟あり)
    else:                  # 末尾の偶数番号は昇格。proof は消費しない
    i = i >> 1;  w = (w + 1) >> 1
合格 ⇔ node == blob ID かつ k == proof の長さ
```

(テストベクタ: 付録 D.3)

#### 7.4.2 P2P での転送

```json
["WANT_BLOB", "<hash hex>", <firstIndex>, <count>]
["BLOB", "<hash hex>", <index>, <totalSize>, "<base64 チャンク>", ["<hex>", …]]
["NOBLOB", "<hash hex>"]
```

- `WANT_BLOB`: 番号 `firstIndex` から最大 `count` 個(`count ≤ 16`)のチャンクを要求する。全体を取るときは `0, 16`(256 KiB 以下ならこれで全部)。
- `BLOB`: **1 フレーム = 1 チャンク**(16 KiB を base64 にして約 21.8 KiB。フレーム上限 64 KiB に収まる)。`totalSize` は blob 全体のサイズ。最後のチャンクだけ 16 KiB 未満でよい。
- 4 番目の配列(証明)は、256 KiB 超の blob のとき**必須**で、§7.4.1 の `proof[]`。256 KiB 以下のときは空配列か省略。
- 受信側の検証
  - 256 KiB 超: **チャンクごとに**証明を検証する(不合格のチャンクは捨てる)。
  - 256 KiB 以下: 全チャンクがそろったあとに、全体の SHA-256 を blob ID と比較する(最大 16 チャンク=256 KiB なので、不合格でも損失は小さい)。
- `NOBLOB`: 持っていない。受信側は別の取得先に切り替える。
- 要求した範囲より多く送ってはならない。レートは §9.1。

#### 7.4.3 HTTP での取得

`home`・`archive` に HTTPS のゲートウェイがあるときは、WebRTC を使わずに HTTP で取得してよい(§11.5)。結果の検証は P2P と同じ(hash / Merkle)で、ゲートウェイを信用する必要はない。

### 7.5 チェックポイントと圧縮(kind 9)

過去の大量イベントを「証明付きの要約」に置き換え、全員が古い本文を持たなくても整合性だけ保てるようにする。

```json
{
  "kind": 9,
  "content": "{\"range\":[0,4999],\"count\":4987,\"root\":\"<merkle root hex>\",\"first_ts\":..., \"last_ts\":...}",
  "tags": [["archive","wss://author.example/lozqul"],["archive","<archive node pk(hex)>"]]
}
```
- 作者が `seq` 範囲ごとに、イベント ID 列の **Merkle ルート**を署名して公開する(3 か月ごと、または 5,000 件ごとが目安)。
- **受信側は範囲内の本文を捨ててよい**。後で必要になれば `archive` タグ先から取得し、Merkle 証明で正しさを検証する。
- 置換型なので最新の checkpoint だけを全員が保持すればよい(範囲は累積可能)。

### 7.6 同期(差分のみ転送)

2 ノード間でフィードを揃えるとき、全件送らない。

1. `HEAD` を交換し、`seq` が同じなら終了。
2. 差があれば `SYNC` で **範囲ベース集合照合(RBSR / negentropy 方式)**:
   - 範囲 `(ts, id)` を分割し、各範囲の XOR/ハッシュのフィンガープリントを交換。
   - 一致しない範囲だけ再帰的に分割し、最終的に差分 ID のみ `WANT`。
3. 通信量は差分件数にほぼ比例し、数万件規模でも 1 往復あたり数 KiB。

### 7.7 拡散(gossip)

リアルタイム配信は **フォローグラフ駆動 + 軽量 gossip**。

- 新イベントを受信したら、(a) そのイベントを購読している全ピアに `EVENT` で転送、(b) それ以外の接続ピアのうち **最大 4 ピア**にだけ `INV [id]` を送る(fanout=4)。
- `INV` を受けて未保持かつ自分に関係(d≤2、またはメンション)あるものだけ `WANT`。
- **重複排除**: 直近 10 分に見た `id` を 64k 件の Bloom / LRU で保持。
- **ホップ制限**: `EVENT`(subId=null)の再拡散は 受信ごとに ttl-1、**初期 ttl=6**(`EVENT` の 4 番目要素)。ttl=0 は転送しない。
- 拡散するのは **d≤2 に該当するか、ピアから明示 SUB されたイベントのみ**。無関係なものを中継して肥大化させない。

### 7.8 削除・編集

- **削除(kind 6)**: `["e", id]` で自作イベントを指す。受信ノードは本文を消し、stub(§7.3)のみ残す。削除要求自体は 365 日で期限切れ。
- 削除は **ベストエフォート**(他ノードが保持を続ける可能性がある)。仕様上の保証はしない。
- **編集**: 投稿は不変。編集は「新しい投稿 + `["replaces", oldId]` タグ」で表現し、クライアントは最新のみ表示する。旧版は通常 TTL で消える。

### 7.9 集計(リアクション数など)

- 反応・リポストは**本体イベントを長期に保存せず**、**閲覧時にローカルで集計**する。
- 古い投稿のカウントを残したい場合、作者が checkpoint の `content` に `"stats":{"<postId>":{"likes":12,"reposts":3}}` を載せる(自己申告。信頼は任意)。

## 8. ダイレクトメッセージ(kind 7)

- **暗号方式**: X25519 の共有秘密 → HKDF-SHA256 → **XChaCha20-Poly1305**。
- **鍵導出**
  ```
  shared = X25519(x_sk_自分, x_pk_相手)          # §3.1 の変換。全ゼロなら拒否
  key    = HKDF-SHA256(ikm = shared, salt = "lozqul-dm-v1",
                       info = min(pkA, pkB) ‖ max(pkA, pkB), L = 32)    # pk は 32 byte の生バイト、辞書順
  ```
- **平文の整形**: `長さ(2 byte, ビッグエンディアン) ‖ UTF-8 本文 ‖ 0x00 のパディング`。全体を **32 byte の倍数(最小 64 byte)** に切り上げる(長さの推測を難しくするため)。本文は 4096 byte 以内。
- **content**: `base64( 0x01 ‖ nonce(24 byte、ランダム) ‖ 暗号文 ‖ タグ(16 byte) )`。先頭の `0x01` は暗号形式の版。
- **AAD**: `送信者 pk(32) ‖ 宛先 pk(32)`(生バイト)。
- **tags**: `["p", "<宛先 hex pk>"]` のみ(必要なら `exp`)。
- **自分宛の暗号化**(mute リストなど): 宛先を自分の `pk` として同じ方式を使う。
- メタデータ(誰が誰に送ったか)は漏れる。秘匿したい場合は将来拡張として Sealed Sender(送信者鍵を暗号化し使い捨て鍵で署名)を予定。
- DM は宛先ノードにだけ保存を要求し、中継ノードは **配送後に即破棄**。受信者がオフラインの場合は、受信者が指定した `relay` / `archive` ノード(プロフィールの `dmrelay`)に最大 30 日預けられる。

## 9. スパム・濫用対策

### 9.1 レート制限(ピアごと)
| 項目 | 既定 |
|---|---|
| EVENT 受信 | 20/秒(バースト 100) |
| 同一作者の新規イベント | 10/分 |
| WANT | 50/秒 |
| SIGNAL | 20/分 |
| WANT_BLOB | 20/秒(応答の合計 1 MiB/秒) |
| 同一作者の kind 0 | 1 件/10 分(§4.5.7) |

### 9.2 発行コスト(任意の Proof of Work)
- `id` の先頭ゼロビット数が `d` 以上であれば PoW 成立(hashcash 方式)。`pow` フィールドで nonce を調整。
- 未知(d=3)の作者のイベントには `d ≥ 16` を要求してよい(ノードの設定)。フォロー中の作者には要求しない。
- 既定難易度は端末で 1 イベントあたり 100 ms 程度に調整。

### 9.3 信頼グラフ
- 拡散・保持の優先度は §7.2 の距離と連動する。**フォロー外の発信は届きにくいが、本人を直接 SUB すれば取得できる**。
- ミュート(kind 8)・ブロックは **ローカルのみで有効**。共有ブロックリストは「購読する第三者リスト」として任意で追加(ユーザーが選んだ場合だけ効く)。

### 9.4 不正イベント
- 署名不正・`id` 不一致・サイズ超過・`ts` 異常は即破棄しピアを減点。
- 同一 `(pk, seq)` で異なる `id` が 2 つ現れたら **フォーク**。両方を証拠として保持し、作者の `uid` に警告を表示する(鍵の漏洩や不具合の兆候)。

## 10. クライアント動作の流れ

### 10.1 初回起動
1. 鍵ペア生成 → `uid` 表示 → profile(kind 0)作成。
2. 招待リンク貼り付け、またはシード接続(§6.1)。
3. PEX・DHT で接続スロットを埋める(§6.2〜6.6)。
4. 自分の `peerRecord` を発行。

### 10.2 フォロー
1. follow(kind 5)を更新(`p` タグ追加)。
2. DHT で `SHA-256("feed:"+pk)` を探索し保持ノードを取得 → `SUB`(`authors`、`since` = 保持期間の下限)。
3. 同期(§7.6)で過去分を補完。

### 10.3 投稿
1. `seq` を +1 し、`exp` を必要に応じ付与して署名。
2. 自分の保存 → 購読ピアへ `EVENT` → 4 ピアへ `INV`。
3. 4 ピア以上に **ACK 相当の `HEAD` 応答**があれば配信成功とみなす(厳密な保証はしない)。

### 10.4 タイムライン
- ローカル DB から `kind ∈ {1,2,3}`、フォロー中作者、新しい順で構築。ネットワーク取得は **差分のみ**。
- d=3 のスレッド表示は一時取得 → LRU(24h)。

### 10.5 推奨ローカル DB スキーマ
```
events(id PK, pk, seq, ts, kind, size, exp, dist, raw BLOB)
INDEX (pk, seq), (kind, ts), (exp), (dist, ts)
stubs(id PK, pk, seq, ts, expire)
peers(pk PK, addr, score, last_ok, caps)
follows(pk PK, since)
blobs(sha256 PK, size, last_access, pinned, bad_until)
gateways(url PK, last_ok, caps, fail_until, token, token_exp)
```

### 10.6 プロフィール画像の設定

1. ユーザーが画像を選ぶ → §4.5.4 の処理(切り抜き・縮小・エンコード・メタデータ除去)を行い、**公開前のプレビュー**(丸・正方形、バナー枠)を見せる。
2. 署名済みの kind 0 を作り、`home` があればゲートウェイへ `event.put` → `blob.put` の順に送る(§11.6、§11.7)。
3. 預かりが成功してから、kind 0 をネットワークへ発行する。ゲートウェイに送れなかったときは、ローカルに「公開待ち」として保存し、バックオフして再試行する。
4. 自分の画像(d=0)は常に pin する(§4.5.7)。

### 10.7 ゲートウェイ経由の初回接続(ブラウザ)

1. 招待リンクの `hint=https://…` から `info`(§11.2)を取得し、`limits` と `caps` を確認する。
2. `challenge` → `auth` でトークンを得る(§11.3.1)。使い捨てのノード鍵で署名する。
3. `peers`(§11.8)で待ち受け中のノードを取得する。署名を検証して候補に加える。
4. 候補に `offer` を `sig.send` し、`sig.poll` で `answer` を受ける(§11.4、§6.5.3)。DataChannel が開いたら `HELLO`。
5. 他者から接続されたいときは `announce` して待ち受けポーリングを始める。
6. 2〜3 本つながったら PEX・DHT(§6.2〜6.4)に移り、ゲートウェイは補助に戻す。

## 11. HTTP ゲートウェイ(CGI 対応)

### 11.1 目的と位置づけ

共有レンタルサーバーのように、**CGI(または PHP)しか動かせず、常駐プロセスも WebSocket も使えない環境**でも、LoℤqUL ネットワークを助けられるようにする補助サービスを定義する。

| 機能 | 内容 | ケイパビリティ |
|---|---|---|
| シグナリング | ブラウザ同士が WebRTC を張るための SDP の受け渡し(メールボックス方式、§11.4) | `signal` |
| ピア紹介 | 待ち受け中のノードのピアレコード(kind 11)の登録と配布(§11.8) | `signal` |
| blob 配信 | プロフィール画像・バナーなどの取得(§11.5) | `blob` |
| 預かり | 自分のイベントと blob を置いておく(§11.6、§11.7) | `store` |
| イベント取得 | 預かったイベントの HTTP での取得(§11.7) | `events` |

- ゲートウェイは**特権を持たない**。イベントは署名付き、blob は hash で自己検証でき、SDP は署名付きなので(§6.5.2)、ゲートウェイを信用しなくても改ざんは検知できる。ゲートウェイが落ちたり悪意を持ったりしても、失われるのは**可用性だけ**で、他の経路(§6.1)で補える。
- ゲートウェイは P2P ノードではない。`HELLO` も DHT も話さず、イベントの gossip(§7.7)にも参加しない。
- 最小構成は **`signal` だけ**(`info`・`challenge`・`auth`・`sig.send`・`sig.poll`・`announce`・`peers`)。`blob` `store` `events` は任意。
- 常駐プロセスを動かせる環境(VPS など)では、ゲートウェイではなく通常のノード(`relay` / `archive`、§5.2)を動かすのが望ましい。

### 11.2 ベース URL とディスカバリ

- **ベース URL**: `https://<host>[:<port>]<path>`(例: `https://example.org/cgi-bin/lozqul.cgi`)。HTTPS 必須(`localhost` は除く)。
- すべての操作は **`op` クエリパラメータ**で選ぶ: `<ベース URL>?op=<操作名>&…`。パス部分(`PATH_INFO`)は使わない(使えない環境があるため)。
- 招待リンクのヒント、プロフィールの `home`(§4.5.1)、ピアレコードの `addr`(§6.3)には、このベース URL をそのまま書く。
- 未知の `op` は `404`(`unknown_op`)。未知のクエリパラメータは無視する。

**操作一覧**

| `op` | メソッド | トークン | 概要 | 必要な cap |
|---|---|---|---|---|
| `info` | GET | 不要 | ゲートウェイの設定を返す | — |
| `challenge` | GET | 不要 | 認証用のチャレンジを返す | `signal` |
| `auth` | POST | 不要 | 署名してトークンを得る | `signal` |
| `sig.send` | POST | 要 | シグナリング本文を宛先のメールボックスへ入れる | `signal` |
| `sig.poll` | GET | 要 | 自分のメールボックスを受信する | `signal` |
| `announce` | POST | 要 | 自分のピアレコード(kind 11)を登録する | `signal` |
| `peers` | GET | 不要 | 登録済みのピアレコードを返す | `signal` |
| `blob` | GET | 不要 | blob 本体を返す | `blob` |
| `blob.put` | POST | 要 | blob を預ける | `store` |
| `event.put` | POST | 要 | イベントを預ける | `store` |
| `events` | GET | 不要 | 預かっているイベントを返す | `events` |
| `head` | GET | 不要 | 作者のフィードの先頭情報を返す | `events` |

**`info`**

```
GET https://example.org/cgi-bin/lozqul.cgi?op=info
```
```json
{"ok":true,"v":1,"name":"example gateway",
 "caps":["signal","blob","store","events"],
 "accounts":"open",
 "limits":{"body":65536,"sig_msg":8192,"mailbox":64,"mailbox_ttl":300,"poll_max":20,
           "blob_max":262144,"blob_quota":5242880,"events_quota":2000},
 "auth_pow":0,
 "ice":[{"urls":["stun:stun.example.org:3478"]}],
 "now":1764000000}
```

| フィールド | 説明 |
|---|---|
| `v` | ゲートウェイ API の版。現在 1 |
| `name` | 表示名(64 byte 以内、任意) |
| `caps` | 提供する機能(上の表の cap) |
| `accounts` | `store` の利用資格。`open`: 認証できた `pk` なら誰でも / `allow`: 運営者の許可リストにある `pk` のみ |
| `limits.body` | POST の本文上限(byte)。`blob.put` を除く |
| `limits.sig_msg` | シグナリング本文の上限(byte)。8192 以上であること |
| `limits.mailbox` / `mailbox_ttl` | メールボックス 1 つの最大メッセージ数 / 保持秒数 |
| `limits.poll_max` | `sig.poll` の `wait` の最大秒数。**0 ならロングポーリング不可**(短周期ポーリングを使う) |
| `limits.blob_max` | `blob.put` の最大サイズ。**262144(256 KiB)以下**であること(§11.6) |
| `limits.blob_quota` / `events_quota` | `pk` ごとの blob 合計バイト数 / イベント件数の上限 |
| `auth_pow` | `auth` に要求する PoW のビット数(0 なら不要。§11.3.2) |
| `ice` | 推奨する STUN(`RTCIceServer` の配列、任意) |
| `now` | サーバーの現在時刻(UNIX 秒)。クライアントは時計のずれの検出に使う |

- `info` のレスポンスは `Cache-Control: public, max-age=300`。クライアントは 5 分以上キャッシュしてよい。
- `info` の値を前提にした動作は、**接続前に必ず `info` を取得してから**行う。

### 11.3 共通ルール

**リクエスト**

- クエリの値は RFC 3986 のパーセントエンコーディング。hex は小文字。
- POST の `Content-Type` は、JSON なら `application/json`、`blob.put` は `application/octet-stream`。本文は UTF-8。
- 本文の長さは `Content-Length` で示す(`Transfer-Encoding: chunked` は使わない。CGI が受け取れないことがある)。無ければ `411`、上限超過は `413`。
- **クッキーを送らない・受け取らない。** クライアントは `credentials: "omit"`、`referrerPolicy: "no-referrer"` で呼ぶ(MUST)。

**CORS**(ブラウザのアプリは別オリジンから呼ぶので必須)

- すべてのレスポンスに次を付ける:
  ```
  Access-Control-Allow-Origin: *
  Access-Control-Allow-Methods: GET, POST, OPTIONS
  Access-Control-Allow-Headers: Content-Type, X-Lozqul-Token
  Access-Control-Max-Age: 86400
  ```
- `OPTIONS` には、`204` と上の CORS ヘッダだけを返す(認証・レート制限の対象外)。
- 認証トークンは **`X-Lozqul-Token` ヘッダ**で送る。`Authorization` ヘッダは使わない(Apache の CGI が渡さない環境があるため)。トークンをクエリに入れてはならない(ログに残る)。

**レスポンス**

- 成功: HTTP `200`(作成時は `201`)、`Content-Type: application/json; charset=utf-8`、本文は `{"ok":true, …}`。ただし `blob` は本体のバイト列。
- 失敗: 本文は `{"ok":false,"err":"<コード>","msg":"<人間向けの説明>"}`。コード一覧は §11.13。
- すべてのレスポンスに `X-Content-Type-Options: nosniff` と `Referrer-Policy: no-referrer`。
- `Cache-Control`: 認証が絡むもの・シグナリング・`challenge` は `no-store`。`peers` と `events` は `public, max-age=15`。`blob` は `public, max-age=31536000, immutable`。

#### 11.3.1 認証(チャレンジ → トークン)

CGI は要求ごとに別のプロセスになり、重い署名検証を毎回行うのは現実的でない。そこで、**署名の検証は最初の 1 回だけ**にして、以降は**状態を持たない HMAC トークン**で認証する。

ゲートウェイは起動時に 32 byte のランダムな秘密 `secret` を 1 つ作って保存する(§11.10)。

**1. チャレンジ**

```
GET ?op=challenge
→ {"ok":true,"chal":"<hex 64 文字>","now":1764000000}
```
```
chal(32 byte) = BE32(ts) ‖ rand(12) ‖ HMAC-SHA256(secret, "chal" ‖ BE32(ts) ‖ rand)[0:16]
```
- `ts` は発行時刻(UNIX 秒)。`chal` は**発行から 60 秒間**有効(時刻が未来にずれた分は 5 秒まで許す)。

**2. 認証**

```
POST ?op=auth
{"pk":"<hex ノード鍵>","chal":"<hex 64>","sig":"<hex 128>","pow":0}
→ {"ok":true,"token":"<base64url>","exp":1764003600}
```

```
sig = Ed25519.sign(node_sk, "lozqul-gwauth-v1\0" ‖ UTF-8(host) ‖ 0x00 ‖ chal(32 byte, 生バイト))
```
- `host` は、クライアントが接続した URL の**オーソリティ**(ホスト名を小文字にしたもの。標準でないポートなら `:ポート` 付き。例: `example.org`、`example.org:8443`)。ゲートウェイは設定の `public_host` と照合する。別のゲートウェイに対する署名を使い回されないための仕組み。
- ゲートウェイは、`chal` の HMAC と有効期限を確認し、`sig` を **strict** に検証する(§3.1)。失敗は `401`(`bad_auth`)。
- 発行するトークン:
  ```
  token(52 byte) = pk(32) ‖ BE32(exp) ‖ HMAC-SHA256(secret, "tok" ‖ pk ‖ BE32(exp))[0:16]
  文字列 = base64url(token)           # パディングなし。70 文字
  exp    = 現在時刻 + 3600(1 時間)
  ```
- トークンは**ノード鍵の所有を示すだけ**で、他の権限は無い。紛失・失効しても、再び認証すればよい。

**3. トークンの使用と検証**

- 要求のヘッダに `X-Lozqul-Token: <文字列>` を付ける。
- ゲートウェイは、base64url を復号して 52 byte か、`exp` が未来か、HMAC が(定数時間比較で)一致するかを確認する。通れば先頭 32 byte が認証済みの `pk`。失敗は `401`(`bad_token`)。
- クライアントはトークンを `exp` の 60 秒前まで使い回し、`401` を受けたら**1 回だけ**再認証してやり直す。
- 運営者が `secret` を差し替えると、すべてのトークンが無効になる(再認証で復旧する)。

#### 11.3.2 認証の PoW(任意)

`info.auth_pow` が 0 より大きいとき、`auth` の `pow` に整数 `n`(0 〜 2^53−1)を入れる。

```
SHA-256( chal(32 byte) ‖ pk(32 byte) ‖ BE64(n) ) の先頭ゼロビット数 ≥ auth_pow
```

`auth_pow` の目安は 0(通常)〜 16(攻撃を受けているとき)。満たさない `auth` は `403`(`pow_required`)。

### 11.4 シグナリング(メールボックス方式)

各ノード(`pk`)に、ゲートウェイ上で**メールボックス**を 1 つ持たせる。送信者が宛先のメールボックスへ本文(§6.5.1 の `body`)を入れ、受信者がそれを**ポーリング**で取り出す。ゲートウェイが SDP を中身ごと覚えるのは、取り出されるまで(最長 `mailbox_ttl` 秒)だけ。

**`sig.send`**

```
POST ?op=sig.send                       X-Lozqul-Token: …
{"to":"<hex pk>","body":{"type":"offer","sid":"…","from":"<hex pk>","ts":…,"sdp":"…","sig":"…"}}
→ {"ok":true,"id":"<メッセージ ID>"}
```

ゲートウェイは次の順に検査する。

1. トークンが有効か。
2. `to` が hex 64 文字か。`body` が §6.5.1 の形式か、UTF-8 の JSON として `limits.sig_msg` 以内か。
3. **`body.from` が、トークンの `pk` と一致するか**(不一致は `403` `from_mismatch`)。
4. `body.type` が `offer` / `answer` / `ice` / `bye` のいずれかか。`offer` / `answer` は `ts` が ±300 秒以内で `sig` を持つか。
5. 宛先が**待ち受け中**か。メールボックスがあり、最後に `sig.poll` された時刻(**在席時刻**。この節の `sig.poll` の説明を参照)から 300 秒以内であること。そうでなければ `409`(`offline`)。送信者はこれを見て別のゲートウェイや経路を試す。
6. レート制限(§11.9)。

通れば、メールボックスの末尾に追加する。メールボックスが `limits.mailbox` 件に達していたら、**最も古いメッセージを捨てて**追加する(送信は断らない)。

- ゲートウェイは `sig` の暗号検証を**してもよい**(MAY)が、必須ではない。**受信者が検証する**(MUST、§6.5.2)。
- 受信者の側から見えるメッセージは、**ゲートウェイが付けた `id` と `ts`(受信時刻)と `body`** だけ。送信者の `pk` は `body.from`(署名で保護)から得る。

**`sig.poll`**

```
GET ?op=sig.poll&since=<id>&wait=<秒>      X-Lozqul-Token: …
→ {"ok":true,"msgs":[{"id":"6924810100000001","ts":1764000000,"body":{…}}, …],
   "next":"6924810100000001","now":1764000001}
```

- `since`: 受け取り済みの最後の `id`。省略または `0` は先頭から。**`since` 以下の `id` のメッセージは削除される**(暗黙の確認応答)。形式が不正なら `400`。
- `wait`: 新着が無いときに待つ最大秒数(0 〜 `limits.poll_max`。既定 0)。待っている間に新着が入ったら、すぐに返す。`poll_max` が 0 のゲートウェイでは `wait` を無視して即座に返す。
- 1 回で返すのは最大 32 件。残りがあれば次の `sig.poll` で取る。
- 新着が無ければ `"msgs":[]`、`"next"` は `since` のまま。
- **配送は at-least-once**。ネットワークの失敗で同じメッセージが再び返ることがある。受信者は `(body.from, body.sid, body.type)` で重複を排除する。
- `sig.poll` を受けたとき、ゲートウェイはそのノードの**在席時刻**(`.seen`)を現在時刻に更新する。

**メッセージ ID**: `id` = 8 桁の hex(受信時刻の UNIX 秒、BE32)+ 8 桁の hex(そのメールボックスごとの連番、1 から)。文字列として辞書順に並べると受信順になる。

**ポーリング周期**

| 状態 | 周期 |
|---|---|
| 接続試行中(offer を送った後、または自分宛の offer を待つ 30 秒間) | `poll_max > 0` なら `wait = min(poll_max, 20)` で連続。`poll_max = 0` なら 1 秒ごと |
| 待ち受け中(他者からの接続を受け付ける) | 20〜60 秒ごと(±20% のゆらぎを付ける) |
| 待ち受けない | ポーリングしない |

- 待ち受け中のノードは、`announce`(§11.8)した `addr` のゲートウェイ(**最大 2 つ**)だけをポーリングする。
- 非表示のタブでブラウザがタイマーを 1 分に間引いても、300 秒の在席判定には間に合う。

### 11.5 blob の取得(`blob`)

```
GET ?op=blob&h=<hex sha256>
→ 200  (本文 = blob のバイト列)
```

- `h` は、ファイル全体の SHA-256(256 KiB 以下の blob、§7.4.1)。
- レスポンスのヘッダ:
  ```
  Content-Type: application/octet-stream
  Content-Disposition: attachment
  Content-Security-Policy: default-src 'none'; sandbox
  ETag: "<h>"
  Cache-Control: public, max-age=31536000, immutable
  Content-Length: <size>
  ```
- ゲートウェイは MIME を判定しない。クライアントは `mime`(kind 0 など)を信用して、§4.5.5 の検査を行う。
- `Range` リクエストは**対応しなくてよい**(blob が最大 256 KiB のため)。`If-None-Match` には `304` を返してよい。
- 持っていなければ `404`(`not_found`)。
- クライアントは受け取った本体の **SHA-256 を必ず `h` と照合する**(MUST)。不一致ならそのゲートウェイを減点する。

> 256 KiB を超える blob(動画など)は、`WANT_BLOB`(§7.4.2)で P2P から取るか、本仕様の範囲外の別の HTTP サーバーに任せる。**CGI ゲートウェイは 256 KiB 以下のみ**を扱う。

**CDN・リライトの利用(任意)**: 運営者は、`/blob/<hash>` のような静的 URL にリライトして CDN に載せてよい。クライアントが使う正規の形は `?op=blob&h=<hash>` のままとする。

### 11.6 blob の預かり(`blob.put`)

```
POST ?op=blob.put&h=<hex sha256>          X-Lozqul-Token: …   Content-Type: application/octet-stream
(本文 = blob のバイト列)
→ 201 {"ok":true,"size":41230}          # 新規
→ 200 {"ok":true,"size":41230,"existed":true}   # すでにある
```

ゲートウェイは次の順に検査する。

1. トークンが有効で、`accounts` が `allow` なら `pk` が許可リストにあるか(無ければ `403` `forbidden`)。
2. `Content-Length` が `limits.blob_max`(≤ 262144)以下か(`413` `too_large`)。
3. 本体の SHA-256 が `h` と一致するか(`400` `hash_mismatch`)。
4. **参照の確認**: `h` が、**同じ `pk` の預かり済みイベント**から参照されているか。参照とは次のいずれか(`409` `unreferenced`)。
   - kind 0 の `icon.hash` または `banner.hash`
   - 任意の kind の `["m", "<h>", …]` タグ
   - kind 12 の `["m", …]` またはその `content` 中の `hash`
5. kind 0 の画像として参照されているとき、本体のマジックナンバーが `mime` と一致し、サイズが §4.5.3 の上限以内か。
6. `pk` ごとの blob の合計が `limits.blob_quota` を超えないか(`507` `quota`)。

> 4 により、ゲートウェイは**任意のファイルの置き場として悪用されない**。画像の公開は「**kind 0 を `event.put` で預ける → `blob.put` で本体を預ける → ネットワークへ kind 0 を発行する**」の順になる(§4.5.4)。

### 11.7 イベントの預かりと取得(`event.put` / `events` / `head`)

自分のノードを常時動かせない作者が、**HTTP だけで自分のフィードを公開する**ための機能。ゲートウェイは gossip には参加せず、受け取ったイベントを蓄えて HTTP で返すだけである。

**`event.put`**

```
POST ?op=event.put                         X-Lozqul-Token: …
{"events":[ {…event…}, … ]}                # 16 件以内、全体で limits.body 以内
→ {"ok":true,"results":[{"id":"…","status":"stored"},{"id":"…","status":"duplicate"},
                         {"id":"…","status":"rejected","err":"sig"}]}
```

- 各イベントを**完全に検証**する: §4.2 の再直列化による `id`、**strict な署名**(§3.1)、`ts` の窓(±10 分)、サイズ(§4.3)、`exp`(PoW は検査しない)。
- **`event.pk` がトークンの `pk` と一致しないものは `rejected`(`pk_mismatch`)**。他人のイベントは預けられない。
- 預かる kind は **0, 1, 2, 3, 5, 6, 9, 10, 12**(運営者が絞ってよい)。DM(kind 7)とピアレコード(kind 11)は受け付けない(kind 11 は `announce`)。
- 置換型(§4.4)は `(pk, kind, d)` ごとに最新の `seq` だけを残す。同じ `(pk, seq)` で `id` が違うものは**フォーク**(§9.4)として `rejected`(`fork`)。
- `exp` が過ぎたものと、既定 TTL(§4.4)を過ぎたものは GC で消す。`pk` ごとに `limits.events_quota` 件まで。超えたら、置換型でない古いものから捨てる。
- 削除要求(kind 6)を受けたら、対象の本文を消して stub だけ残す(§7.8)。

**`events`**

```
GET ?op=events&authors=<hex>,<hex>&kinds=0,1&since=1763000000&until=…&seqFrom=100&limit=50
→ {"ok":true,"events":[ {…}, … ],"more":false}
```

- パラメータは §5.4 のフィルタと同じ意味(`authors` は 16 個まで、`kinds` は 8 個まで、`limit` は最大 200・既定 50)。`e` と `p` のフィルタは対象外。
- 新しい順(`ts` の降順、同じなら `id`)。レスポンスは最大 1 MiB。切り詰めたときは `"more":true`。
- 返すイベントの形式は P2P の `EVENT` と同じ(未知のフィールドは除く)。**クライアントは受け取った各イベントの `id` と署名を必ず検証する**(MUST)。

**`head`**

```
GET ?op=head&pk=<hex>
→ {"ok":true,"seq":128,"id":"<hex>","ts":1764000000}
```
預かりが無ければ `404`。クライアントは `HEAD`(§5.3)の代わりに使って差分の有無を調べ、`events` の `seqFrom` で続きを取る。

### 11.8 ピア紹介(`announce` / `peers`)

待ち受け中のノードを見つけやすくして、**シードの代わり**にもなる機能。

**`announce`**

```
POST ?op=announce                          X-Lozqul-Token: …
{"event":{…kind 11 のイベント…}}
→ {"ok":true}
```

- イベントは §6.3 のピアレコード。`pk` がトークンの `pk` と一致し、署名が有効で、`ts` が 24 時間以内であること。
- `addr` には、このゲートウェイのベース URL を**含めるべき**(SHOULD。他のゲートウェイや `wss://` も併記してよい)。
- ゲートウェイは `pk` ごとに最新の 1 件だけを保持し、`ts` から 24 時間で消す。登録は 1 時間に 10 回まで。

**`peers`**

```
GET ?op=peers&n=16
→ {"ok":true,"peers":[ {…kind 11…}, … ]}
```

- 最大 `n`(既定 16、最大 16)件のピアレコード。**待ち受け中**(在席から 300 秒以内)のものを先に、残りを後に、それぞれランダムな順で返す。
- クライアントは署名と `ts` を検証してから候補テーブルに加える(§6.2 の PEX と同じ)。
- これで、**ゲートウェイの URL を 1 つ知っているだけで、他のブラウザノードを紹介される**。

### 11.9 レート制限と容量

既定のレート制限(運営者が変えてよい)。超過は `429`(`rate_limited`)と `Retry-After`(秒)を返す。

| 対象 | 制限 |
|---|---|
| IP アドレスごと(全操作の合計) | 120 回/分 |
| IP アドレスごと(`challenge` + `auth`) | 10 回/分 |
| `pk` ごとの `sig.send`(合計 / 宛先 1 つあたり) | 30 回/分 / 10 回/分 |
| `pk` ごとの `sig.poll` | 120 回/分 |
| `pk` ごとの `blob.put` | 10 回/分 |
| `pk` ごとの `event.put` | 30 回/分 |
| `pk` ごとの `announce` | 10 回/時間 |

- IPv6 は /64 を 1 つの IP として数える。
- **容量**: 運営者は、全体のディスク使用量の上限(`data_max`)と、メールボックスの総数の上限(既定 10,000)を設定する。超えたときの新規の書き込みは `503`(`full`)。

### 11.10 CGI 実装ガイド

#### 11.10.1 動作環境

- 言語は問わない。Ed25519 の **strict 検証**(§3.1)と HMAC-SHA256、SHA-256 が使えること。
  - PHP 7.2 以降(`sodium_crypto_sign_verify_detached`。ただし `S < L` などの strict 検査は別途確認する)
  - Python 3(PyNaCl / `cryptography`。純 Python の実装は 1 回の検証に数十 ms かかるが、署名検証は `auth` と `event.put` だけなので許容できる)
  - Perl(CryptX)、Ruby、Node.js など
- CGI は `REQUEST_METHOD`・`QUERY_STRING`・`CONTENT_LENGTH`・`REMOTE_ADDR`(レート制限用)を読み、標準出力に `Status:` ヘッダ + ヘッダ + 空行 + 本文を書く。
- **データディレクトリは、公開ディレクトリ(ドキュメントルート)の外**に置くか、Web からの参照を拒否する(付録 E.1)。

#### 11.10.2 ファイル配置(DB なし)

```
<data>/
  gateway.json                  設定(public_host, name, accounts, limits, ice, auth_pow, data_max)
  secret                        32 byte の乱数(0600)。トークン・チャレンジ用の HMAC 鍵
  allow.txt                     (accounts=allow のとき)許可する pk を 1 行 1 個(hex)
  mbox/<pk hex>/
      .seen                     空ファイル。mtime = 最後に sig.poll された時刻(在席)
      .counter                  次のメッセージ連番(flock で保護)
      <id>.json                 メッセージ {"id":"…","ts":…,"body":{…}}
  peers/<pk hex>.json           announce されたピアレコード(kind 11)
  ev/<pk hex>/<seq 10 桁>.json   預かったイベント(置換型は (kind, d) ごとの最新のみ)
  ev/<pk hex>/head.json         {"seq":…,"id":"…","ts":…}
  blob/<hh>/<sha256 hex>        blob 本体(hh = hash の先頭 2 文字)
  blob/<hh>/<sha256 hex>.meta   {"pk":"…","size":…,"created":…}
  quota/<pk hex>.json           {"blob_bytes":…,"events":…}
  rl/<種別>-<キー>-<分>         レート制限の分ごとのカウンタ(1 行に整数)
  gc.lock                       GC の排他用
```

- **ファイル名に使うのは、検証済みの hex(`^[0-9a-f]{64}$` など)・数字・固定の名前だけ**。利用者の入力を、そのままパスに入れてはならない(パストラバーサル対策、MUST)。
- 書き込みは「同じディレクトリに一時ファイルを作る → `rename(2)` で置き換える」で原子的にする。連番の採番と、メールボックスの追加・削除は `flock` で排他する。

#### 11.10.3 処理の流れ

```
main():
    設定を読む
    if メソッド == OPTIONS: 204 + CORS ヘッダ を返して終了
    IP のレート制限を数える(超過なら 429)
    op に応じて分岐(未知なら 404)
        (token が要る op は §11.3.1 の検証を先に行う)
    応答を返す
    確率 1/50 で gc() を実行(gc.lock を取れたときだけ)
```

**GC**(`gc()`。cron が使えるなら、cron から定期的に呼んでもよい)

- メールボックス: `mailbox_ttl` を過ぎたメッセージを削除する。`.seen` が 24 時間より古いメールボックスはディレクトリごと削除する。
- `peers/`: `ts` から 24 時間を過ぎたものを削除する。
- `rl/`: 2 分より古いものを削除する。
- `ev/`: `exp`・既定 TTL(§4.4)を過ぎたものを削除し、`events_quota` を超えた分を古い順に削除する。
- `blob/`: 預かり済みのどのイベントからも**参照されていない** blob を、`created` から 30 日(§4.5.7)後に削除する。1 日に 1 回までの実行でよい。

#### 11.10.4 長いポーリングについて

- ロングポーリングは、CGI プロセスを**待たせたまま保持**する。実装は 0.5 秒ごとにメールボックスのディレクトリを調べ、`wait` 秒に達するか新着があるまで繰り返す。
- 共有サーバーはプロセス数や実行時間(30 秒前後)に上限があることが多い。そのような環境の運営者は、`limits.poll_max` を **0**(ロングポーリング無し)にするか、10 以下にする。`poll_max` は実行時間の上限より十分に短くする。
- ロングポーリングの有無で、プロトコルの動作は変わらない。

#### 11.10.5 セキュリティ要件(まとめ)

- **MUST**: 入力の検証(hex・長さ・数値の範囲)をしてからファイルに触れる。本文は `Content-Length` までしか読まない。JSON の入れ子は深さ 8 まで。
- **MUST**: HMAC の比較は定数時間で行う。`secret` を応答・ログに出さない。
- **MUST**: `blob` のレスポンスに `Content-Security-Policy: default-src 'none'; sandbox` と `Content-Disposition: attachment` を付ける(ブラウザが直接開いても何も実行されないように)。
- **MUST**: DM(kind 7)を預からない。`mute`(kind 8)など暗号文を、運営者が読める形で保存しない。
- **SHOULD**: アクセスログに、トークン・クエリの `h` 以外の値・本文を記録しない(IP・時刻・`op`・ステータスだけ)。保持は 24 時間以内。
- **SHOULD**: PHP の `display_errors` などを切り、エラー内容を利用者に返さない(`500` `internal` だけ)。

### 11.11 プライバシーと運営

ゲートウェイの運営者は、次の情報を**観測できる**。

- 接続元の IP アドレスと、認証に使われた `pk` の対応
- 誰が誰(`to`)に接続しようとしたか、その時刻
- 渡された SDP に含まれる、双方の IP アドレス候補
- どの blob・イベントを、いつ取得したか

軽減策:

- ブラウザは**使い捨てのノード鍵**(§3.4)を使う。ユーザー鍵とノード鍵を結び付けない。
- 複数のゲートウェイを使い分ける(§11.12)。
- 運営者は、ログを最小限(IP・時刻・`op`・ステータス)にして 24 時間以内に消す(SHOULD)。
- 運営者は、ゲートウェイが**鍵・秘密・平文の DM を扱わない**ことを利用者に明示する。

### 11.12 クライアントの動作

- **ゲートウェイの一覧**は、招待リンクの `hint`、相手の `addr` と `home`、`peers`、`seeds.json` から集め、最大 16 件を保持する。最近成功したものを優先する。
- **接続前に `info`**: 取得に失敗するゲートウェイは、一定時間(10 分 → 1 時間 → 24 時間と延ばして)使わない。`info.now` が自分の時計と ±120 秒以上ずれていたら、ユーザーに警告する。
- **複数経路で送る**: 相手の `addr` に `https://` が 2 つ以上あるとき、最初のゲートウェイへ送り、**5 秒**応答が無ければ(`offline` を含む)次のゲートウェイにも同じ `sid` で送る。
- **待ち受け**: 待ち受けるノードは、信頼できる 2 つ以内のゲートウェイに `announce` し、そこだけをポーリングする(§11.4)。
- **blob・イベントの取得先**: 作者の `home` → 取得に失敗したら他の経路(§4.5.7)。受け取った内容は、必ず自分で検証する(hash・署名)。
- ゲートウェイからの `409` `offline` は、相手が待ち受けていないという意味で、エラーではない。別の経路に切り替える。

- 未知の `kind` は **保存・中継せず無視**(ただし署名が有効なら、d≤1 では保存してよい)。

### A.2 gossip

### E.5 参考コード: チャレンジとトークン(Python)

§11.3.1 の規則と付録 D.4 のテストベクタに一致することを確認済みの実装。

```python
import hmac, hashlib, struct, base64, os, time
from nacl.signing import VerifyKey
from nacl.exceptions import BadSignatureError

def _mac(secret, *parts):
    return hmac.new(secret, b"".join(parts), hashlib.sha256).digest()[:16]

def make_challenge(secret, now=None, rnd=None):
    ts = struct.pack(">I", int(now if now is not None else time.time()))
    rnd = rnd if rnd is not None else os.urandom(12)
    return ts + rnd + _mac(secret, b"chal", ts, rnd)            # 32 byte

def check_challenge(secret, chal, now):
    if len(chal) != 32: return False
    ts, rnd, mac = chal[:4], chal[4:16], chal[16:]
    if not hmac.compare_digest(mac, _mac(secret, b"chal", ts, rnd)): return False
    t = struct.unpack(">I", ts)[0]
    return now - 60 <= t <= now + 5

def verify_auth(pk, chal, sig, host):
    msg = b"lozqul-gwauth-v1\0" + host.encode() + b"\0" + chal
    try:
        VerifyKey(pk).verify(msg, sig); return True              # strict 検査(S<L 等)は別途確認すること
    except BadSignatureError:
        return False

def make_token(secret, pk, exp):
    e = struct.pack(">I", exp)
    raw = pk + e + _mac(secret, b"tok", pk, e)                   # 52 byte
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode()

def check_token(secret, token, now):
    try:
        raw = base64.urlsafe_b64decode(token + "=" * (-len(token) % 4))
    except Exception:
        return None
    if len(raw) != 52: return None
    pk, e, mac = raw[:32], raw[32:36], raw[36:]
    if not hmac.compare_digest(mac, _mac(secret, b"tok", pk, e)): return None
    if struct.unpack(">I", e)[0] <= now: return None
    return pk                                                    # 認証済みの pk
```

> PyNaCl(libsodium)の `verify` は RFC 8032 の `S < L` を検査する。非正準な `A` / `R` や小位数点の拒否(§3.1)は、ライブラリによって挙動が違うので、使うライブラリの仕様を確認し、必要なら別途検査を加える。
